# Bitget 全倉合約自動化與測試額度

伺服器取得 Bitget USDT 永續已收盤 1H K 線，以 4H 判斷盤勢，經本人授權與風控後呼叫正式合約 API。原生停損／目標、委託去重、未知回應保留及成交對帳沿用既有引擎。程式及資料庫更新不會啟用任何帳戶的 LIVE。

## 全倉資金配置

新合約自動化明確使用 `crossed` 全倉保證金。使用者自行於 Bitget 劃轉 USDT，系統不自動劃轉或借款。每次進場唯讀交易所 USDT 淨值與可用保證金，採實際資金計算，不使用設定頁的研究本金。UTA 其他抵押幣不列入本功能的下單本金；Classic 限 USDT 單資產帳戶。

- 單筆名目倉位上限可設本金 **3～5%**，預設 5%。百分比指槓桿後總部位；槓桿不額外放大計算出的數量。
- 同時持倉上限 **1～3 筆**，預設 3。D1 原子保留名額；待成交及結果未知仍占用名額。既有同環境加密貨幣部位也列入限制。
- 單筆計畫停損風險最多本金 0.25%，同方向總計畫風險最多 0.5%；因此實際數量可能低於 3%。每日虧損、交易次數與連敗冷卻仍受風控限制。
- 全倉依帳戶總保證金、其他部位與資金變動決定強平風險，不顯示逐倉的單筆強平估價。檢查可用保證金、費用／停損預留與維持保證金緩衝，並保存交易所原生停損／目標。

目前修改範圍為即時自動化。既有歷史回測仍使用單資產逐倉強平壓力模型；該結果不等於全倉帳戶的歷史強平或資金使用結果。

## 全市場掃描與手動部位共存（2026-10-14）

- **合約範圍**可選「指定商品（最多五個）」或「全部 Bitget USDT 永續」。全市場模式在 `symbols_json` 保存為 `["*"]`，不需資料庫更新。
- 全市場清單每十分鐘由公開行情重算：正常交易的 USDT 永續，24H 成交額 ≥ **1,000 萬 USDT**，**包含股票、黃金、原油等 RWA 合約**，依成交額排序。2026-10-14 實測約 55 個（加密幣 30、RWA 25）。
- 新倉流動性門檻同步由 5,000 萬降為 1,000 萬（`FUTURES_MIN_QUOTE_VOLUME_USDT`），指定商品模式也適用；價差 ≤ 0.15% 與名目 ≤ 附近深度 1% 兩道檢查不變。
- 掃描順序為本系統持倉、已有 K 線快取、尚未暖機。持倉商品跌出門檻後仍持續檢查出場。歷史不足 824 根的新商品會顯示「暫停」，超過五分鐘窗口後當小時不再重抓。
- 同時持倉上限（最多 3 筆）、單筆 0.25% 風險、同方向 0.5% 風險都不變；全市場只是擴大候選，不會增加同時部位數。
- **手動部位**：其他幣種有手動部位時，自動化照常開倉；該幣種已有任何方向的部位（含手動單）時跳過，稽核為 `REJECTED`。策略風險額度只計本系統部位；全倉保證金安全由交易所實際可用 USDT 與維持保證金檢查，這兩項已包含手動部位的影響。本系統的出場、停損備援與對帳只處理自己建立的部位。
- 已知限制：本系統持有某幣時，若你再手動對同幣同方向加倉，部位會在交易所合併。系統平倉前偵測到持倉量大於自己的紀錄就會停止並要求人工核對，不會連同手動部分一起平掉；但交易所原生停損可能作用在合併後的整個部位上，請避免對系統持有的幣種手動下單。

## 30U 只用於測試

「測試單」才套用 `maxNotionalUsdt`，可設 5～30 USDT 的**名目部位**上限；這不是保證金。選「依帳戶本金配置」後，忽略此固定額度，改依上述本金百分比風控。兩種額度模式與 Demo／LIVE 環境分開設定；LIVE 測試單也是真實委託。

低於交易所最小數量時拒單，不向上湊單、不人工製造訊號。歷史回測參數不會套用到即時自動化。市價單額度是行情與單邊 10 bps 滑價預留的估算；測試單若對帳確認超額，五分鐘備援保護會要求退出，仍可能產生滑價與費用。

資料庫更新 `0027_futures_test_budget.sql` 新增測試開關、百分比與持倉上限，並停止舊設定的新倉授權，使用者需檢查全倉配置後重新儲存。

## 啟用前的唯讀檢查

1. 使用 Node.js 20.19.6，以 `npm run dev:demo` 開啟本機網站。此指令強制禁止 LIVE 新倉，即使 `.dev.vars` 誤設正式政策也不放行。
2. 本人登入 [設定頁](http://localhost:5190/settings)，將完整三項金鑰保存在「正式合約專用憑證」。一般 Bitget API 與 Demo 欄位不會搬入正式合約；金鑰於伺服器加密保存，前端只顯示綁定狀態。
3. 在 [合約頁](http://localhost:5190/crypto-futures)選 LIVE，按「檢查 LIVE 帳戶（唯讀）」。只呼叫帳戶 GET，不更改模式／槓桿或建立委託；讀取成功不能證明寫入交易權限成功。
4. 按「預覽目前設定（不送單）」。只預覽清單第一個商品，使用表單策略、槓桿、額度模式與倉位百分比；確認進場時會唯讀本人 USDT 資金。沒有確認訊號時不顯示虛構進場倉位，不啟用或儲存自動化。
5. Slack Bot 必須已加入指定合約頻道。token 與頻道 ID 存在只是設定完成，不代表訊息已送達。

UTA 使用 V3；Classic 在 V3 明確回覆 `40084`（Classic 帳戶不支援 UTA API）後改查 V2；另保留 `40099` 舊相容分支。兩種環境保持各自金鑰及 `paptrading` 設定。UTA 需帳戶管理與交易權限，參考 [官方帳戶 API](https://www.bitget.com/docs/catalog/account/account-settings)及[官方委託 API](https://www.bitget.com/docs/catalog/trading/order-management)。

## 本人啟用正式自動化

以下操作會讓後續確認訊號建立真實委託，須由本人完成：

1. 設定頁選正式合約 LIVE、確認正式憑證與槓桿，開啟「允許 LIVE 真實下單」。
2. 停止舊開發程序，自行以 `npm run dev:trading` 啟動本機執行器。該指令開放本機 Demo／LIVE 政策，仍需每個帳戶授權；普通 `dev` 或 `dev:demo` 不會開放 LIVE。
3. 合約頁選 LIVE、商品、策略、測試或本金配置、單筆 3～5% 與最多三筆，勾啟用與真實資金授權再儲存。後端再次讀取正式帳戶驗證後才保存啟用設定。
4. 每分鐘檢查收盤訊號，超過五分鐘的進場不追補。委託接受與已成交分開顯示，正式／模擬訊號與帳本均分開。

下單前重新核對設定版本、環境、額度、實戰授權、風控與憑證。中途停止或改額度使舊掃描失效；已送出的委託仍可能成交。有未確認委託或未平倉部位時，禁止切換環境、商品或策略。

## 停止與目前限制

「停止自動新倉」撤回本人新倉授權，不受操作冷卻限制。已有委託與部位須持續對帳；程序運作時保留原生停損、五分鐘備援與時間退出。關閉 Node 或電腦休眠會停止本機排程，交易所已接受的委託與原生保護仍留在 Bitget。

這是本機測試執行器；長期運作須有持續開機、可連線 Bitget 的主機。本機與 Cloudflare D1 的帳號／金鑰／設定不同步。同一本機 D1 只開一個開發伺服器，建置前先停止它。

Cloudflare 正式自動化政策仍為 `false`，先前獨立部署 Worker 實測 Bitget 回覆 403，確切安全規則尚未釐清，升級方案不保證解除。先前本機 Node／curl 另遇 TLS／DNS 失敗；2026/10/13 直接唯讀原始回應確認：UTA V3 回覆 `40084`，文字說明是 Classic 帳戶不支援 Unified Account API；同一正式憑證查 Classic V2 帳戶成功回覆 `00000`。已修正交易與帳本的帳戶辨識，只有已知相容回應才查 V2，簽章或權限錯誤仍中止。不得停用 TLS 驗證繞過。

本次測試用隔離 D1、假金鑰與攔截 fetch。真實委託與成交仍須於可連線環境由本人啟用後確認，不能以合成測試視為真實交易成功。

資金與槓桿欄位依 [Bitget UTA 資金文件](https://www.bitget.com/legacy-docs/uta/account/Get-Account)及 [Classic 帳戶文件](https://www.bitget.com/docs/catalog/classic-contract-account/classic-contract-account)。唯讀成功與合成測試通過都不代表真實委託已成交。
