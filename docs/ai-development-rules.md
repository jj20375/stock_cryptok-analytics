# AI 開發規則

本文件是本專案所有 AI 工具與開發者共同遵守的規範，適用於 Claude、Codex、Antigravity、Antigravity IDE 與其他自動化程式碼代理。

## 核心原則

- 所有新增與修改的原始碼檔案，單一檔案不得超過 1000 行。
- 單一檔案超過 800 行時，必須優先規劃拆檔。
- 單一檔案已超過 1000 行時，不得繼續加入新功能；只能進行拆檔、修 bug、刪除死碼或搬移邏輯。
- 規則適用於 `app/`、`drizzle/`、根目錄工具腳本與所有手寫程式碼。
- `node_modules/`、`build/`、`.wrangler/`、自動產生檔案、lockfile 與第三方套件不受 1000 行限制。

## 拆檔規則

- React 頁面檔超過 800 行時，應拆成 `components`、`hooks`、`utils`、`types` 與 `constants`。
- API route 應只保留 request/response、驗證與服務呼叫，不應塞入大量商業邏輯。
- Service 檔超過 800 行時，應依領域拆分，例如市場資料、技術指標、策略判斷、通知、風控、報表。
- 單一函式超過 80 行時，必須檢查是否能拆成具名 helper。
- 單一 React component 超過 250 行時，必須拆出子 component 或 hook。
- 單一區塊若同時處理 UI、資料轉換、交易策略與副作用，必須拆開。

## 目前需優先拆解的檔案

- `app/routes/home.tsx` 已完成第一階段拆解，目前低於 1000 行；後續新增首頁功能時，仍應放入 `app/features/home/` 對應模組，不要重新塞回 route 檔。
- `app/services/stockService.ts` 已超過 1000 行，後續新增功能前應優先拆成資料抓取、技術指標、策略評估與市場工具函式。
- 具體拆分步驟請參考 `docs/refactor-plan.md`。

## 註解規則

- 所有註解一律使用繁體中文。
- 註解要說明「為什麼這樣做」，不要只描述程式碼表面動作。
- 任何 workaround、fallback、相容性處理、風控、交易限制、排程限制與資料格式轉換，都必須加註解。
- 金融策略相關註解必須寫明使用的指標、門檻、時間週期、交易方向與風險假設。
- 涉及真實交易、下單、排程通知、Slack/Telegram 發送與資料庫寫入時，註解必須說明副作用與失敗風險。

## 變數註解規則

- 重要變數必須有繁體中文註解，包含用途、單位、來源與風險含義。
- 交易策略變數必須註明指標意義，例如 RSI、EMA、MACD、Supertrend、ATR、布林帶、成交量均線。
- 門檻變數必須註明為何選用該值，例如 `rsiOversold = 15` 代表極端超賣，不是一般超賣。
- 時間變數必須註明時區、週期與用途，例如台股日報排程應明確標示 `Asia/Taipei`。
- 金額、價格、比例、百分比與數量變數必須註明單位。
- 環境變數與 secret 名稱必須註明用途，但不得在註解中寫入真實值。
- 簡單迴圈索引、明顯的解構暫存值與只在 1 至 2 行內使用的局部變數，可免除逐一註解。

## 命名規則

- 變數名稱必須能看出用途，不得使用含糊名稱如 `data2`、`temp`、`result1`。
- 金融策略變數應保留常見技術名詞，例如 `ema200`、`rsi14`、`macdSignal`、`atrStopLoss`。
- 布林帶、均線、RSI 等策略計算應使用一致命名，避免同一概念出現多種名稱。
- 布林帶上軌使用 `upperBand` 或 `bollingerUpper`，下軌使用 `lowerBand` 或 `bollingerLower`。
- 與 AI 分析、排程、通知、交易副作用相關的函式名稱，必須清楚表明動作與目標。

## AI 執行規則

- 修改程式前，先檢查目標檔案行數；若超過 1000 行，先拆檔再新增功能。
- 若使用者要求快速修 bug，可以在超過 1000 行的檔案中做最小修正，但修正後必須回報此檔仍需拆解。
- 不得為了通過 1000 行限制，把檔案拆成無語意的碎片。
- 不得把大型共用型別、常數與工具函式全部塞進單一 `utils.ts`。
- 新增策略時，應優先建立可重用的 strategy module，再由 UI 圖層引用。
- 新增註解時，不要塞滿噪音；但重要變數、風控條件、策略門檻與副作用一定要說明。

## 驗證規則

- 完成修改後，至少執行 `npm run build`，除非任務明確不涉及程式碼或環境無法執行。
- 若 build 失敗，必須先修復由本次修改造成的錯誤。
- 若存在既有警告，應在回報中標明是否與本次修改有關。
- 若新增拆檔，必須確認 import/export 路徑正確。

## 回報格式

- 回報時先說明完成什麼，再列出修改檔案。
- 若仍有超過 1000 行的檔案，必須列出並建議下一步拆解順序。
- 若因任務範圍未能完成拆檔，必須明確說明原因與後續建議。
